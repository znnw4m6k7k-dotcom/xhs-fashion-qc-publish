# 女装生图、审图、卖点文案与发布编排

把一次女装小红书任务收敛为一条可复用闭环。默认输入不是只有图片，还包括产品名和本款卖点；默认图片是 5 张街拍＋1 张对镜自拍；默认 RedBeacon 入口是“自主添加笔记”，不调用 RedBeacon 生图、文案生成或付费改写。

## 能力分工

按以下顺序调用现有能力，不重写底层生图、质检或发布能力：

1. `xiaohongshu-fashion-prompt-draw`：从权威服装参考图和身份锚点生成本地图片。
2. `fashion-ai-image-qc` 或现有独立商品图审图能力：逐张对照服装参考图，给出 A/B/C 结论。
3. 本编排层：把用户卖点整理为产品事实卡，生成有依据的标题、正文和标签。
4. `redbeacon-review` / `redbeacon-publish`：把合格图文放入指定账号的本地审稿台，经人工审核和最终发布确认后发布。

## 输入契约

每次任务先锁定以下信息；账号必须由用户明确指定，不能沿用上一次账号：

- 小红书账号：`account_id` 与账号名。
- 产品名称。
- 至少一张可读的本地权威服装参考图；有正面、背面和细节图时全部检查。
- 同一人物身份锚点（用户提供的人像或已接受的系列锚点）。没有锚点时，不能承诺跨图人物完全一致。
- 用户提供的本款卖点：版型、领口、面料、穿着感受、适用场景、搭配方向等。
- 可选的视觉参考 HTML 或抽卡页面。它只提供构图、动作、表情、背景和场景灵感，不覆盖服装事实，也不替代用户本次任务。

七维抽卡默认读取本 Skill 内置的 `references/xhs-photography-prompt-deck.json`，因此不依赖某台电脑上的绝对 HTML 路径。用户提供新的 HTML 时，可作为本次任务的临时覆盖来源；需先抽取并确认仍是七维结构，再记录它的文件路径和选卡结果。

把产品信息分成三层：

- `image_verified`：图片中可见并确认的结构、颜色、轮廓、肌理。
- `user_provided_selling_points`：用户明确提供但未必能从图片单独验证的卖点；文案中可以使用，但要避免绝对承诺。
- `unknown_or_unsupported`：未看到或未提供的后背结构、口袋、内里、成分比例、产地、价格、库存、数据等；不得补写。

“进口”“遮副乳”“不挑身形”“显瘦”“长度不压身高”等词，只有在用户提供充分证据且平台表达允许时才可原样使用；默认改成克制的体验描述，并提示实际效果受身形、尺码、搭配和环境影响。

## 不可突破的边界

- 必须先检查权威服装参考图，再生图；不能用产品名或静态文字代替服装参考图。
- 图片服务使用当前宿主的原生图像生成能力。禁止调用 RedBeacon 生图、图片兜底、文案兜底和付费审稿改写；需要这些能力时标记 `BLOCKED`。
- 服装结构、颜色和套装边界优先于任何风格、场景或抽卡结果。
- 6 张图必须全部获得独立质检 `A`；`B` 不能直接计入交付，`C` 只能针对失败维度重试一次或淘汰。
- 不直接写 RedBeacon SQLite、不直接改浏览器 profile；只使用 CLI 和 UI。
- 自主添加入口会把稿件显示为用户自主添加，通常不会写入 AI 来源字段。不能因此伪造图片来源；真实生图来源、参考图和声明设置必须写入 run manifest。
- 不得把“上传完成”“提交成功”当成“已发布”。必须有发布成功信号和本地归档回读。

## 产品事实卡与文案契约

生图前建立产品事实卡；写文案前再次读取同一张卡。每篇文案都必须回答：这件衣服看得见的结构是什么、用户卖点对应哪种穿着体验、适合什么具体场景。

推荐写作顺序：

1. 用本款真实结构或面料细节开头，不沿用旧 SKU。
2. 把用户卖点翻译成版型感受、走动效果、触感或搭配场景。
3. 对舒适、修饰、包容类卖点使用克制表达，不做身材或效果保证。
4. 最后给出具体的搭配问题，避免空泛互动。

如果用户要求长期更新账号风格，可单独更新 `land` 的 `copy_guide`，写入“每条先读取本条产品事实与卖点卡”；这只是长期规则，不能替代本次运行把卖点实际写入事实卡、文案和 RedBeacon 入审稿件。

## 运行清单与结构闸门

从 `references/run-manifest-template.json` 创建 UTF-8 JSON，放在最终图片目录旁边。运行清单至少记录：账号、产品事实、用户卖点、未知信息、权威参考图、身份锚点、每张图的路径和 A 级结论、文案、RedBeacon 审稿记录、发布结果、AI 声明设置和实际发布服务费。

先做本地结构闸门，再交给 RedBeacon：

```text
python3 scripts/validate_run_manifest.py \
  --manifest <run-manifest.json> \
  --expected-count 6 \
  --expected-account-id <account_id> \
  --require-selling-points \
  --require-copy
```

自主添加入审成功、拿到审稿记录后再做一次完整闸门：

```text
python3 scripts/validate_run_manifest.py \
  --manifest <run-manifest.json> \
  --expected-count 6 \
  --expected-account-id <account_id> \
  --require-selling-points \
  --require-copy \
  --require-redbeacon
```

校验失败就是 `BLOCKED`，不能绕过质检、强行映射图片或直接写数据库。

## 工作流

### 1. 锁定产品并生成 5＋1 图片

使用 `xiaohongshu-fashion-prompt-draw`：

- 生成产品事实卡和未知字段清单。
- 固定同一身份锚点，不能让不同生成图互相污染身份。
- 默认规划 6 张 3:4 竖图：5 张街拍、1 张对镜自拍。
- 每张图单独调用一次原生生图并检查，不一次生成“六宫格”。
- 记录 `generation.provider=native-image-generation`、`generation.redbeacon_fallback_used=false`、`generation.platform_generation_points_used=0`。

### 2. 使用抽卡式视觉变量，但服装优先

默认使用内置抽卡库；或在用户提供随机抽卡 HTML 时，将它作为本次任务的覆盖来源。按七个维度为每张图选卡：构图、姿势、光线、景深、表情、背景、场景。每张图的卡片组合、卡片 ID、来源（`builtin-deck` 或外部 HTML 路径）都要写入清单。

内置抽卡库只负责可迁移的“抽卡数据”，不是需要启动的网页。若用户想在另一台电脑上手动点击抽卡，可自行把原 HTML 放在任意位置；自动工作流仍以随 Skill 迁移的 JSON 为准。

- 至少 4 张保持完整服装可读；5 张街拍要有不同机位、环境和动作。
- 默认不把人物固定在画面中央；使用三分法、框景、引导线、对角线、留白等偏位构图。
- 表情必须有自然变化：低头浅笑、侧望、行走专注、轻笑、回眸或松弛状态；拒绝僵硬直视和重复站桩。
- 背景要有真实环境层次，如树影、建筑、栏杆、画廊、街角外摆等；不得出现可读品牌、菜单、路牌或文字。
- 抽卡结果不能新增领口、门襟、口袋、腰带、印花、后背结构或第二件服装。
- 对镜自拍只保留一个人物和一个真实镜像，手机不能遮住脸、领口或关键服装结构。

### 3. 逐图独立质检

让独立质检能力逐张检查权威参考图与候选图，至少覆盖：服装结构、颜色、纹理、人物一致性、表情动作自然度、偏位构图、场景有效性、重复度、文字水印和品牌安全。

不合格图只允许针对失败维度重试一次，例如只修复领口、手部或表情，不同时改变服装、人物和场景。最终不足 6 张 A 图时，停止并报告缺口。

可保留必要的量化证据（尺寸、黑色暗部、边缘/纹理指标），但量化结果不能替代逐图视觉判断。

### 4. 根据卖点生成文案

文案必须读取本次产品事实卡和用户卖点，不能只读取账号定位或上一款稿件。标题、正文、标签全部写入 manifest，并使用同一份内容入审。

如果用户没有提供关键卖点，不自行补齐；采用保守的可见事实文案，或停下来请求产品事实。禁止使用 RedBeacon 生成、改写或付费 review rewrite 来补文案。

### 5. 以自主添加方式进入 RedBeacon

当用户指定“不用 RedBeacon 算力、使用自主添加”时：

1. 先确认账号登录和 6 张 A 图、标题、正文、标签齐全。
2. 使用 `review create --account-id <ID> --data-file <UTF-8 JSON>`，JSON 只包含 `title`、`body`、`tags`、`image_paths`。
3. 成功后记录 `redbeacon.review_record_id`，再次运行带 `--require-redbeacon` 的 manifest 闸门，并打开指定账号的审稿页。
4. 不自动通过、不自动发布；审稿页只是让用户看到结果。

自主添加不需要 topic record ID 或 plan ID；不要为了满足旧模板虚构选题和方案编号。若改走 RedBeacon 正常生成工作包，必须另行记录真实的 batch/generation/topic/plan ID，并且禁止平台兜底。

### 6. 审核与发布

1. 用户明确认可后，才把本条标为通过；用户说“可以发布”属于发布授权，但仍要先核对下面的精确预览。
2. 每次发布前验证指定小红书账号登录态。
3. 运行发布预览，向用户展示标题、正文摘要、图片数量、立即/定时、可见范围、AI 声明、浏览器显示设置和可见的发布服务费。
4. 如果用户要求“零点发布”，而预览没有明确返回费用为 0，费用就是未知，必须停在发布前，不得把未知当作免费。
5. 只有用户确认这份精确预览后才发布。发布服务费与生图/文案算力分开记录；实际结算以后端回执和余额回读为准。
6. 发布后回读成功信号、本地归档、可用笔记链接和结算后余额。链接为空时如实记录为空，不编造 URL。

## 停止状态

遇到以下任一情况，停止并报告确切原因：

- 缺少权威服装参考图、必要身份锚点或关键产品事实。
- 少于 6 张独立 A 图，或出现结构、身份、文字/品牌安全问题。
- 需要 RedBeacon 生图、文案兜底、付费改写或其他平台生成能力。
- 账号不明确、账号掉线、图片数量与入审数量不一致。
- 发布预览费用未知但用户要求零点，或费用非 0 且用户未授权该费用。
- 缺少用户对精确发布预览的最终确认。
- 只有提交成功/上传完成，没有发布成功信号和归档回读。
